# Bron–Kerbosch: максимальные клики на CPU и CUDA

Учебно-исследовательский проект: находит **все максимальные клики**
неориентированного графа двумя способами — последовательно на CPU
(референс) и параллельно на GPU (CUDA). Включает генератор тестовых
графов и автоматическую сверку результатов между реализациями.

---

## 1. Постановка задачи

**Задача:** для заданного неориентированного графа найти множество всех его максимальных клик (подмножеств вершин, любые две из которых соединены ребром, и которые нельзя расширить добавлением новой вершины).

Сложность этой задачи заключается в том, что их число может быть экспоненциальным по размеру графа (например, у графа Муна–Мозера из 3n вершин ровно 3^(n/3)
максимальных клик).

## 6. Формат входного файла

```
N
u1 v1
u2 v2
...
```

- первая строка — число вершин `N > 0`;
- далее — по ребру на строку, `u v`, `0 ≤ u, v < N`;
- порядок `u`/`v` не важен, рёбра дублируются автоматически;
- self-loops и выходы за диапазон игнорируются.

## 8. Запуск

### 8.1. Общий синтаксис

```
bk_test --file <graph.txt> [флаги]
bk_test --generate <N> <density_%> [--seed <N>] [флаги]
bk_test --generate <N> --edges <M> [--seed <N>] [флаги]
bk_test --gen-by-cliques <M> <density_%> [--seed <N>] [флаги]
```

Флаги:

| Флаг | Значение |
|------|----------|
| `--cpu-only`     | запустить только CPU-версию |
| `--gpu-only`     | запустить только CUDA-версию |
| `--no-verify`    | не сверять результаты CPU и GPU |
| `--quiet`        | минимум вывода |
| `--gpu-blocks N` | ограничить число CUDA-блоков (0 = авто, для strong scaling) |
| `--save <path>`  | сохранить построенный/загруженный граф в файл |
| `-h`, `--help`   | показать справку |

### 8.2. Примеры CPU

```bash
# Плотный граф: 200 вершин, 50 %
./bk_test --generate 200 50 --cpu-only

# Ровно 2000 рёбер
./bk_test --generate 1000 --edges 2000 --cpu-only

# Воспроизводимый прогон с фиксированным seed
./bk_test --generate 5000 1 --seed 123 --cpu-only
```

### 8.3. Примеры CUDA

```bash
# Только GPU, без сверки
./bk_test --generate 5000 2 --gpu-only --no-verify

# Разреженный большой граф (в пределах MAX_VERTICES)
./bk_test --generate 10000 1 --gpu-only
```

### 8.4. Совместный запуск со сверкой

```bash
./bk_test --generate 1000 10
./bk_test --file graph.txt
```

### 8.5. Генерация по числу максимальных клик и сохранение

```bash
# Граф с не менее 10 000 максимальных клик при плотности 10%
./bk_test --gen-by-cliques 10000 10 --gpu-only

# Тот же граф, но с сохранением в файл и фиксированным seed
./bk_test --gen-by-cliques 10000 10 --seed 42 --save graph_10k.txt
```

`--gen-by-cliques M p` принимает плотность `p` в процентах и строит
граф, добавляя вершины и рёбра до достижения не менее `M` максимальных
клик (фактическое число может на 1–5 превышать `M`).

## 9. Генерация тестовых графов

Встроенный генератор детерминирован по `seed` — одинаковые параметры
дают одинаковый граф.

| Способ | Команда |
|--------|---------|
| G(N, p%) по Эрдёшу–Реньи | `./bk_test --generate N p` |
| Ровно M различных рёбер  | `./bk_test --generate N --edges M` |
| Не менее M максимальных клик | `./bk_test --gen-by-cliques M p` |
| Задать seed              | `--seed <число>` (по умолчанию 42) |

`--gen-by-cliques M p` принимает плотность `p` в процентах и строит
граф, добавляя вершины и рёбра до достижения не менее `M` максимальных
клик (фактическое число может на 1–5 превышать `M`).

Позиционная запись seed тоже поддерживается:
`--generate 1000 10 123` эквивалентно `--generate 1000 10 --seed 123`.

  распараллелить, а `atomicAdd` становится узким горлышком.

## 11 Сильная и слабая масштабируемость
### 11.1 Сильная масштабируемость

**Определение.** Сильная масштабируемость (strong scaling) — зависимость
производительности `R` от числа параллельных единиц `p` при фиксированной
вычислительной сложности задачи `W = const`. В наших экспериментах
`W` фиксируется графом (V, p%, seed), а `p` — это число CUDA-блоков
(`--gpu-blocks`), размер блока везде 128.

**Метрики:**
- `T(p)` — время ядра в миллисекундах (cudaEvent);
- `S(p) = T(1) / T(p)` — ускорение;
- `E(p) = S(p) / p` — эффективность (идеал = 1.0).

### Условия экспериментов

- GPU: Tesla K40s (Kepler, sm_35), 15 SM, 11.4 ГБ;
- CUDA 11.1, gcc 9.1, `-O3`, seed = 42;
- раздел `test` кластера «Ломоносов-2».

### Анализ результатов.
Масштабируемость реализации можно условно разделить на три режима. На малом числе блоков (<math>p \le 4</math>) наблюдается почти линейное ускорение с эффективностью <math>E(p) \approx 0.86 - 1.00</math>. При дальнейшем росте до <math>p \le 64</math> наступает насыщение, и эффективность падает до 0.3–0.6. Выше 64 блоков наступает плато, где увеличение <math>p</math> не даёт прироста.

Максимальное ускорение <math>S_{\max}</math> растёт с размером задачи: от 16 раз на 99 тысячах клик до 27 раз на 4 миллионах. Это связано с тем, что больший граф обеспечивает лучшую загрузку блоков. Однако существует и физический предел: на K40s всего 15 SM, поэтому ускорение выше 15 достигается лишь за счёт одновременного исполнения нескольких блоков на одном SM (occupancy > 1).

Основные причины отклонения от идеала — это конкуренция за атомарный счётчик atomicAdd при миллионах клик, неравномерность нагрузки (разные пары (v, c) дают разное число клик, а статический grid-stride не балансирует их), а также пропускная способность глобальной памяти (матрица смежности для n = 10000 занимает ~128 МБ).

Практический вывод: для каждого графа есть свой оптимум p* (например, 64 для V=1000 и 128 для V=10000), после которого наращивать число блоков бесполезно — это лишь расходует ресурсы GPU-узла.

### 11.2. Слабая масштабируемость

**Определение.** Слабая масштабируемость (weak scaling) — сохранение
времени выполнения при одновременном пропорциональном увеличении числа
параллельных единиц `p` и размера задачи, то есть при фиксированном объёме
работы на одну единицу: `W/p = const`.

**Постановка.** Для задачи перечисления максимальных клик объём входных
данных (`|V| + |E|`) не отражает вычислительную сложность — она
определяется структурой дерева рекурсии. В качестве единицы работы выбрано
число максимальных клик `μ(G)`. Условие: `μ(G)/p = C = 10 000` клик на
один запрошенный CUDA-блок.

Здесь `p` — **запрошенное** число CUDA-блоков (`--gpu-blocks`). Фактическое
`grid` ограничено occupancy и числом SM (см. таблицу): при `p ≥ 32` на K40s
запускается `grid = 30`. После этого предела эксперимент проверяет уже не
слабую масштабируемость в исходной постановке, а поведение реализации при
фиксированном числе реальных блоков и растущей очереди задач.

**Генератор.** Использован `generateByMaxCliques`, который строит граф
фиксированной плотности 10% (модель Эрдёша–Реньи), добавляя вершины и рёбра
до достижения **не менее** `μ = p·C` максимальных клик.

**Методика.** Для каждой точки — 5 прогонов после одного прогревочного; в
таблице медиана. Разброс ≤ 0.5% для `T_kernel` и ≤ 2% для `T_total`.
`T_kernel` — `cudaEvent` вокруг ядра; `T_total` включает выделение памяти,
H2D, ядро, D2H и декодирование.

**Условия.** Tesla K40s (Kepler, sm_35, 15 SM, 11.4 ГБ), CUDA 11.1,
gcc 9.1, seed = 42.

**Наблюдения.**

Идеальная слабая масштабируемость не достигается: T_kernel монотонно растёт с p (с 26.5 мс при p=1 до 239.9 мс при p=64, то есть примерно в 9 раз). T_total при этом меняется немонотонно (83 -> 77 -> 81 -> 90 -> ...), так как на малых графах доминируют фиксированные накладные расходы на копирования. Рост T_kernel объясняется тем, что при фиксированной плотности 10% для пропорционально большего μ размер графа N должен расти (433 -> 1900 вершин); вместе с N растут множества P и X, глубже рекурсия, дороже обработка каждого задания (v, c). Метрика μ/p фиксирует число выходных данных, но не сложность промежуточных шагов.

Аппаратное насыщение наступает при p ≥ 32, когда реальное grid становится равным 30 (15 SM × occupancy 2). Дальнейший рост p не добавляет параллельных мощностей и лишь удлиняет очередь задач. Формально после p ~ 30 эксперимент проверяет уже не слабую масштабируемость в исходной постановке, а поведение реализации при фиксированном числе реальных блоков и растущей очереди задач — это видно по колонке μ/grid.

В результате проведённых измерений можно сделать вывод, что условие μ(G)/p = const является необходимым, но недостаточным для слабой масштабируемости в данной задаче. Объём промежуточных вычислений (размеры P, X, глубина обхода) на одно задание (v,c) растёт вместе с N, поэтому добавление новых параллельных единиц не компенсирует рост стоимости обработки задания.

## 12. Ограничения и известные проблемы

### 12.1. `MAX_VERTICES = 10240` (только GPU)

GPU-версия не обрабатывает графы с `n > 10240`. CPU-версия ограничена
только временем и объёмом RAM.

**Причина.** `P`, `X`, `R` — битовые маски фиксированной ширины.
Длина маски `NW = ceil(n / 32)` должна быть compile-time константой
шаблона, чтобы `nvcc` мог развернуть циклы и держать `Frame` в
локальной памяти. Для `n = 10240` `NW = 320`, `Frame` ~ 3.8 КБ.

### 12.2. `MAX_DEPTH = 20` (только GPU)

Клики размером > 20 вершин не будут найдены:ядро пропускает ветку без предупреждения при переполнении стека. Проверяйте результат сверкой с CPU
(по умолчанию включена; отключается флагом `--no-verify`).

Когда срабатывает. Для графов с плотностью ≤ 10% при `n ≥ 100` максимальный размер
клики редко превышает 10. Порог 20 выбран с запасом. Проблема возникает
на плотных маленьких графах (`n = 50`, `плотность = 90%`) — там используйте
`--cpu-only`.

### 12.3. `maxCliques = 1 << 22` (~ 4.2M клик, только GPU)

Если у графа больше максимальных клик, они **молча теряются** (счётчик
растёт, но в буфер пишутся только первые 4M). После копирования на хост
`runBronKerboschCUDA` это обнаруживает и кидает `std::runtime_error`.

**Причина.** Буфер клик — линейный массив масок: `maxCliques × NW × 4`
байт. При `NW = 320` это 1.28 КБ на клику, и 4M клик ~ 5.4 ГБ VRAM.

**Обход.** Поднять до `1 << 23` (~ 10.8 ГБ — только на картах с 24+ ГБ)
или запустить `--cpu-only`.

### 12.4. Графы, которые не имеет смысла подавать на GPU

`G(50000, 0.5)` содержит ~ 6·10⁸ рёбер, число максимальных клик —
астрономическое.

### 12.5. Долгая сборка

Комбинация «несколько архитектур × несколько инстанцирований шаблона
ядра» даёт заметное время компиляции. Решение — одна архитектура
(`native`) и только нужные `NW` в `switch`.

### 12.6. `Unsupported gpu architecture 'compute_35'`

CUDA ≥ 12 удалила поддержку Kepler. Если нужна именно sm_35, используйте
CUDA 11.8 и драйвер R470. Современные карты собираются под свою
архитектуру без потери функциональности.
