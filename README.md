# Bron–Kerbosch: максимальные клики на CPU и CUDA

Учебно-исследовательский проект: находит **все максимальные клики**
неориентированного графа двумя способами — последовательно на CPU
(референс) и параллельно на GPU (CUDA). Включает генератор тестовых
графов и автоматическую сверку результатов между реализациями.

---

## 1. Постановка задачи

**Задача перечисления всех максимальных клик:**
необходимо перечислить все максимальные клики.

Сложность этой задачи заключается в том, что их число может быть экспоненциальным по размеру графа (например, у графа Муна–Мозера из 3n вершин ровно 3^(n/3)
максимальных клик).

## 3. Требования

- **ОС:** Linux (проверено на Ubuntu 22.04).
- **GPU:** NVIDIA. Локально тестировалось на GeForce RTX 3050 Laptop (8 ГБ, sm_86).
- **CUDA Toolkit:** ≥ 11.0. Для Kepler (sm_35) нужен CUDA 11.x —
  в CUDA ≥ 12 поддержка sm_35 удалена.
- **Компиляторы:** GCC/G++ ≥ 9 или Clang ≥ 10; `nvcc` из CUDA Toolkit.
- **CMake:** ≥ 3.18. Для `-DCMAKE_CUDA_ARCHITECTURES=native` — ≥ 3.24.

## 6. Формат входного файла

```
N
u1 v1
u2 v2
...
```

- первая строка — число вершин `N > 0`;
- далее — по ребру на строку, `u v`, `0 ≤ u, v < N`;
- порядок `u`/`v` не важен, рёбра дублируются автоматически;
- self-loops и выходы за диапазон молча пропускаются.

## 8. Запуск

### 8.1. Общий синтаксис

```
bk_test --file <graph.txt> [флаги]
bk_test --generate <N> <density_%> [--seed <N>] [флаги]
bk_test --generate <N> --edges <M> [--seed <N>] [флаги]
```

Флаги:

| Флаг | Значение |
|------|----------|
| `--cpu-only`     | запустить только CPU-версию |
| `--gpu-only`     | запустить только CUDA-версию |
| `--no-verify`    | не сверять результаты CPU и GPU |
| `--quiet`        | минимум вывода |
| `--gpu-blocks N` | ограничить число CUDA-блоков (0 = авто, для strong scaling) |
| `-h`, `--help`   | показать справку |

### 8.2. Примеры CPU

```bash
# Плотный граф: 200 вершин, 50 %
./bk_test --generate 200 50 --cpu-only

# Ровно 2000 рёбер
./bk_test --generate 1000 --edges 2000 --cpu-only

# Воспроизводимый прогон с фиксированным seed
./bk_test --generate 5000 1 --seed 123 --cpu-only
```

### 8.3. Примеры CUDA

```bash
# Только GPU, без сверки
./bk_test --generate 5000 2 --gpu-only --no-verify

# Разреженный большой граф (в пределах MAX_VERTICES)
./bk_test --generate 10000 1 --gpu-only
```

### 8.4. Совместный запуск со сверкой

```bash
./bk_test --generate 1000 10
./bk_test --file graph.txt
```

## 9. Генерация тестовых графов

Встроенный генератор детерминирован по `seed` — одинаковые параметры
дают одинаковый граф.

| Способ | Команда |
|--------|---------|
| G(N, p%) по Эрдёшу–Реньи | `./bk_test --generate N p` |
| Ровно M различных рёбер  | `./bk_test --generate N --edges M` |
| Задать seed              | `--seed <число>` (по умолчанию 42) |

Позиционная запись seed тоже поддерживается:
`--generate 1000 10 123` эквивалентно `--generate 1000 10 --seed 123`.

  распараллелить, а `atomicAdd` становится узким горлышком.

## 11. Сильная масштабируемость

**Определение.** Сильная масштабируемость (strong scaling) — зависимость
производительности `R` от числа параллельных единиц `p` при фиксированной
вычислительной сложности задачи `W = const`. В наших экспериментах
`W` фиксируется графом (V, p%, seed), а `p` — это число CUDA-блоков
(`--gpu-blocks`), размер блока везде 128.

**Метрики:**
- `T(p)` — время ядра в миллисекундах (cudaEvent);
- `S(p) = T(1) / T(p)` — ускорение;
- `E(p) = S(p) / p` — эффективность (идеал = 1.0).

### Условия экспериментов

- GPU: Tesla K40s (Kepler, sm_35), 15 SM, 11.4 ГБ;
- CUDA 11.1, gcc 9.1, `-O3`, seed = 42;
- раздел `test` кластера «Ломоносов-2».

### Наблюдения

1. **Три режима масштабируемости:**
   - `p ≤ 4` — почти линейное ускорение, `E(p) ~ 0.86–1.00`.
   - `4 < p ≤ 64` — насыщение, `E(p)` падает до 0.3–0.6.
   - `p > 64` — плато: дальнейший рост блоков не сокращает `T(p)`.

2. **`S_max` растёт с размером задачи:**
   - 99 тыс. клик → `S_max ~ 16`
   - 1.19 млн клик → `S_max ~ 22`
   - 3.7–4.1 млн клик → `S_max ~ 26–27`

3. **Практический оптимум `p*`** (где `T(p)` перестаёт уменьшаться):
   - V = 1000 → `p* ~ 64` (дальше — плато 17.8 мс)
   - V = 5000 → `p* ~ 128` (дальше — плато 7.3 с)
   - V = 10000 → `p* ~ 128` (**при 180 блоках время даже чуть растёт** —
     4403 мс против 4337 мс)

4. **Причины отклонения от идеальной масштабируемости:**
   - конкуренция за `atomicAdd(cliqueCount, 1)` — общий счётчик для
     миллионов клик;
   - неравномерная нагрузка: разные пары `(v, c)` порождают разное
     число клик, статический grid-stride не балансирует;
   - пропускная способность глобальной памяти: `adjMask` при
     `n = 10000, NW = 320` занимает ~128 МБ, все блоки читают его
     одновременно;
   - фундаментальный предел: 15 SM на K40s, значит «идеального»
     ускорения > 15 достичь нельзя без occupancy > 1. Реально получено
     16–27× — SM исполняют несколько блоков одновременно.

5. **Практический смысл.** Для каждого графа есть `p*`, после которого
   дальнейшее увеличение `p` бесполезно. Знание `p*` позволяет не
   тратить ресурсы GPU-узла на лишний параллелизм.

## 12. Ограничения и известные проблемы

### 12.1. `MAX_VERTICES = 10240` (только GPU)

GPU-версия не обрабатывает графы с `n > 10240`. CPU-версия ограничена
только временем и объёмом RAM.

**Причина.** `P`, `X`, `R` — битовые маски фиксированной ширины.
Длина маски `NW = ceil(n / 32)` должна быть compile-time константой
шаблона, чтобы `nvcc` мог развернуть циклы и держать `Frame` в
локальной памяти. Для `n = 10240` `NW = 320`, `Frame` ~ 3.8 КБ.

### 12.2. `MAX_DEPTH = 20` (только GPU)

Клики размером > 20 вершин **не будут найдены**: ядро молча пропускает
ветку при переполнении стека. Проверяйте результат сверкой с CPU
(по умолчанию включена; отключается флагом `--no-verify`).

**Когда срабатывает.** Для `p ≤ 0.1` при `n ≥ 100` максимальный размер
клики редко превышает 10. Порог 20 выбран с запасом. Проблема возникает
на плотных маленьких графах (`n = 50, p = 0.9`) — там используйте
`--cpu-only`.

### 12.3. `maxCliques = 1 << 22` (~ 4.2M клик, только GPU)

Если у графа больше максимальных клик, они **молча теряются** (счётчик
растёт, но в буфер пишутся только первые 4M). После копирования на хост
`runBronKerboschCUDA` это обнаруживает и кидает `std::runtime_error`.

**Причина.** Буфер клик — линейный массив масок: `maxCliques × NW × 4`
байт. При `NW = 320` это 1.28 КБ на клику, и 4M клик ~ 5.4 ГБ VRAM.

**Обход.** Поднять до `1 << 23` (~ 10.8 ГБ — только на картах с 24+ ГБ)
или запустить `--cpu-only`.

### 12.4. Графы, которые не имеет смысла подавать на GPU

`G(50000, 0.5)` содержит ~ 6·10⁸ рёбер, число максимальных клик —
астрономическое.

### 12.5. Долгая сборка

Комбинация «несколько архитектур × несколько инстанцирований шаблона
ядра» даёт заметное время компиляции. Решение — одна архитектура
(`native`) и только нужные `NW` в `switch`.

### 12.6. `Unsupported gpu architecture 'compute_35'`

CUDA ≥ 12 удалила поддержку Kepler. Если нужна именно sm_35, используйте
CUDA 11.8 и драйвер R470. Современные карты собираются под свою
архитектуру без потери функциональности.
